# Лабораторная работа 7. Кураторство активности и происхождение данных

**Привязка:** [глава 7](../../Module_theory/Module%207_Database.md). **Режим:** локальный CPU; сначала выполненный пример, затем новая задача. **Автор и аффилиация:** владелец курса заполняет при публикации. **Ориентир времени:** 60–120 минут для большинства работ; для QSPR и докинга дополнительно учитывайте запуск и разбор.

## Сущность и назначение

Отделить сопоставимые точные наблюдения от других endpoint, границ и неизвестных единиц. Работа проверяет не только исполнение кода, но и допустимость вывода. До запуска сформулируйте ожидаемый результат и один случай, в котором алгоритму нельзя доверять.

## Данные и постановка кейса

activities.csv — восемь искусственных записей; esol.csv — отдельный настоящий открытый корпус. Полное происхождение, единицы, тип данных и ограничения находятся в [паспорте datasets](../datasets/README.md). Искусственные значения не смешиваются с реальными измерениями. Каждый вход сохраняется с идентификатором и hash; генерируемые результаты записываются в `Labs/results/lab07/`.

## Workflow

**Схема → endpoint/мишень/ассей → единицы/отношение → журнал → snapshot hash.**

Разделите три этапа: проверка входа, применение метода и оценка результата. Успешный запуск не отменяет проверки химической формы, единиц, состояния модели и независимости сравнения.

## Guideline: пошаговый разбор

1. Прочитайте условия консервативной политики T1/A1/IC50/=.
2. Преобразуйте только положительные концентрации с известными единицами.
3. Сохраните восемь исходных строк и причины шести исключений, отдельно прочитайте паспорт ESOL.

Откройте [notebook](../notebooks/lab07.ipynb) и выполните ячейки сверху вниз с чистым ядром. Первая ячейка находит корень репозитория, затем задаются DATA/OUT. Следующая содержит полный код данного кейса с проверками. Последняя сохраняет `benchmark.json`: параметры, артефакты и время расчётной части. Ошибка assert означает, что результат нужно исследовать; удалять проверку ради прохождения нельзя.

Вставки `# WHY` и объяснения в теории связывают вызовы с научным смыслом. Если основной алгоритм вынесен в общий модуль, прочитайте его исходник по ссылке из notebook: общий код нужен, чтобы CLI, ноутбук и приложение использовали одну политику.

## Benchmark и критерии приёмки

Включены R01/R02 с pIC50=7; в журнале все 8 строк; остальные причины различимы.

Время измеряется на конкретном компьютере и не служит обещанием ускорения. Эталонные показатели проверенного запуска находятся в [сводном benchmark](../benchmarks/REPORT.md). Числа с плавающей точкой сравниваются с допуском, стохастические результаты — по явно указанным инвариантам. Наличие правильного ответа в книге не заменяет фактический запуск вашего кода.

2. Добавьте Ki с тем же числом и объясните, почему это не новый IC50.
3. Спроектируйте pagination/timeout для API, не запрашивая закрытые данные.

**Сдача:** notebook после Restart & Run All, таблица/рисунок из OUT, три предложения «наблюдение — ограничение — следующее действие». Не сдавайте только скриншот зелёной ячейки. Через 7 дней выполните первое упражнение на новом вводе без копирования ответа.

## Оценка

10 баллов: 2 за вход и происхождение, 3 за корректный запуск и проверки, 3 за интерпретацию, 2 за самостоятельный перенос. Обязательны сохранение ошибочных записей там, где это предусмотрено, отсутствие выдачи прогнозов за измерения и явный режим фактического исполнения тяжёлого инструмента.
