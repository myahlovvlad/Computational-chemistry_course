# Стандарт исследовательских практикумов — Notebook-first (v1, пилот)

**Дата:** 2026-11-17. **Статус:** решение автора принято, стандарт пилотируется в модуле 1; не объявлять все 28 блокнотов созданными.
**Приоритет:** замещает старую схему «один короткий ноутбук + отдельные арифметические задачи без процесса». Предшествующий аудит GitHub Issue #1 сохраняется, но теперь должен оценивать не только работоспособность, а и педагогическую состоятельность.

## 1. Смысл практикума

Студент принимает осмысленные решения в химическом исследовании, а не исполняет команды из списка. У каждого блока есть **достоверная исследовательская проблема**, участники/контекст без фиктивной «лаборатории Химера», ограничения, ожидаемый научный результат и последствия неверного решения.

**Цикл исследования:** ситуация → вопрос → исходные данные и происхождение → прогноз до расчёта → выбор представления/метода → пошаговый расчёт → визуализация → обнаружение скрытого нюанса → проверка модели/данных → обоснованное решение → что нужно измерить дальше.

**Каждый модуль = ровно два основных Jupyter Notebook:**
1. `01_guided_case.ipynb` — **исследовательский разбор** полностью выполненного, проверенного кейса: связный естественный текст + фрагменты кода + фактические значения/графики + анализ результата, типичные ошибки и выводы. Обязательно объяснять *зачем* запускается ячейка, *что* показал результат и *какое* ограничение осталось.
2. `02_independent_lab.ipynb` — **лабораторный практикум** из 2–4 связанных, но не копирующих разобранный пример кейсов, возрастающая самостоятельность, ввод и expected artifacts, подсказки по запросу, автоматические проверки инвариантов без раскрытия целевых ответов, итоговый мини-отчёт/решение.

К обоим: `README.md` (вход/цели/время/источники/маршрут/проверки), `data/` только при необходимости, `tests/` и `instructor/` для закрытых эталонов/рубрики (не выдавать полный ответ учащемуся в его учебном файле). Точные артефакты и виды тестов зависят от научной задачи, но файлы основных ноутбуков обязательны для всех 14 модулей.

**Сквозное правило:** студент знает, какую конкретную неопределённость устраняет каждый шаг, и обнаруживает как минимум один существенный скрытый нюанс (потеря химической идентичности; неверная единица; утечка данных; отсутствие повторов; некорректная метрика; различие энергии и барьера; ограничение скоринговой функции). «Сюрприз» не должен зависеть от обмана или научной ошибки автора.

## 2. Методическая архитектура

### Notebook 1 — guided case
- Начальная ситуация и **требующий решения научный вопрос**, реальный/условный контекст явно размечен.
- Контрольный прогноз: допустим неверный ответ без штрафа.
- Структура входных данных и вопрос о качестве наблюдений.
- Код чередуется с объяснением конкретной гипотезы, величины и переменных (одна идея за шаг).
- Физическая интерпретация графика; оси, единицы, допущения.
- Разбор неожиданного или ошибочного результата (например, конфликт способов измерения).
- Контрольные тесты; нельзя путать выполнение скрипта с валидацией физической модели.
- Обсуждение альтернативного метода и критерия следующего эксперимента.
- Явно сформулированный **научный итог** с неопределённостью, а не просто «код отработал».
- Обновление объяснённой связи в междисциплинарной карте.

### Notebook 2 — independent lab
- 2–4 связанные кейса с вводной историей и конкретной ролью студента в решении; перенос на новые данные.
- Вопрос выбора метода до предоставления команд; студенту нельзя просто повторить ответ из Notebook 1.
- Прогрессия: управляемая задача → частично заданный pipeline → самостоятельный выбор и интерпретация.
- Подготовленные начальные данные, заполняемые клетки, чекпоинты с понятной обратной связью.
- Обязательны сценарии ошибочного/неполного ввода и вынужденного уточнения гипотезы.
- Ожидаемый артефакт: таблица, график, протокол, вывод и план следующего эксперимента.
- Самопроверка научных **инвариантов** и формата; решения, ключи и hidden tests в материалах преподавателя.
- Умение сообщить «данных недостаточно» считается проверяемой компетенцией.

## 3. Программная среда и IDE

- `SETUP_WINDOWS_LINUX.md`: инструкция для Windows 10/11 и Linux (включая не Ubuntu-дистрибутивы), проверка Python/venv/JupyterLab, выбор kernel, пути, отсутствие глобальной установки и smoke test. Для Linux-пакетов не давать единой недостоверной команды для всех дистрибутивов.
- Отдельные requirements для базового курса и тяжёлых модулей. В будущем после CI зафиксировать версии зависимостей и хеши для поддерживаемых ОС.
- Код в notebook фокусируется на **исследовании и объяснении**. Если задача — написать приложение, CLI, библиотеку, сервис, UI или сложную архитектуру, работать в IDE и хранить код в `src/`, тесты в `tests/`; Notebook используется для исследования данных, прототипирования, верификации и отчёта. **Не превращать Notebook в IDE для приложения.**
- Обязательные пути для слабого CPU: небольшой самостоятельный пример и документированный исходный output тяжёлого расчёта для самостоятельного разбора, с ясным указанием происхождения.

## 4. Связь с теорией и Stepik

- Сначала разработать проверяемую структуру исследований и задания, затем адаптировать учебные объяснения под требуемые действия и типичные ошибки; научные источники проверяются заранее.
- В Stepik не заменять лабораторный notebook только тестом на одно число. После локального исполнения обязательны анализ графика, обоснование вывода и интерпретация ограничения.
- Встраивание произвольного JS и ноутбуков в grader не предполагается; форматы оценивания проверить отдельно.
- Блокноты не должны подсовывать тяжёлый setup в первый модуль: модуль 1 работает со стандартным Python и matplotlib; RDKit вводится позже по потребности.

## 5. Acceptance criteria для пилота и масштабирования

- В каждой паре ровно два основных корректных `.ipynb`, валидная структура JSON nbformat, проверенный порядок исполнения ячеек на заявленной среде.
- Guided case полностью исполняется на подготовленных данных; в выходах есть как минимум одна верифицируемая численная величина и визуализация с интерпретацией, если она помогает решению.
- Independent lab запускается с чистого kernel; незаполненные задачи дают доступную подсказку, а не traceback.
- Отдельно запускать instructor solution / reference tests и фиксировать среды, seed, версии, исходные данные, результаты.
- Подлинная мотивация и последовательность исследовательских решений, хотя конкретный численный пример может быть явно *синтетическим*.
- Указаны ограничения, возможные ошибки и следующий эксперимент; нет утверждений о статистической значимости без оценки разброса.
- В карту знаний добавляется осмысленная связь с объяснением, а не декоративный узел.
- Независимый студент без устного пояснения преподавателя может ответить: что выясняли, зачем метод, что нашли, что нельзя заключать.

## 6. Организация работ

1. Сначала пилотировать модуль 1 с двумя notebook на материале DoE-кейса, отделив учебную статистику от реальных результатов.
2. Проверить академическую пригодность, воспроизводимость и понятность на небольшом круге студентов.
3. Затем применить стандарт к модулю 3 (молекулярная идентичность) и модулю 12 (QM), чтобы проверить перенос шаблона на разные типы задач.
4. После этого создавать оставшиеся пары, используя общую рубрику и автоматическую проверку.
5. По завершении всех обязательных практикумов адаптировать теоретические тексты и готовить публичный релиз.
